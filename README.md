# 読み方判定デモ (Kanji Reading Checker)

漢字氏名とふりがな(カナ)を受け取り、[Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)(TypeSafe
AIのSystem Oneモデル)の3つのプリミティブで「その読み方がどの程度一般的か」を6観点から判定する
Next.jsアプリです。画面は1つ(`/`)だけで、1280×720にスクロールなしで収まります。

TypeSafeの[公式APIとJavaScript SDK](https://docs.typesafe.ai/sdk/javascript)(`@typesafe-ai/sdk`)を
直接呼び出します。Vercel AI Gatewayは経由しません。

## 構成

```
app/
  page.tsx                     唯一の画面。入力・Jevの返り値・しきい値判断の3セクション
  api/analyze-reading/route.ts 6観点まとめて評価するAPI(画面が使う)
  api/verify-reading/route.ts  noul 1問だけの軽量API(画面からは未使用。一括処理用に残置)
  components/
    analysis-report.tsx        6観点の値の表示 + しきい値判断の表示・読み解きの生成
    insight-row.tsx            観点1つぶんの行(プリミティブ名・期待値・confidence・分布)
lib/
  jev-client.ts                TypeSafeClientの遅延生成とテスト用の差し替え型
  verify-reading.ts            noul 1問での判定と閾値によるverdict判定
  analyze-reading.ts           6観点(noul×1 / choice×2 / score×3)を1リクエストで評価
  normalize-reading.ts         ふりがなをひらがなに正規化(表記ゆれの吸収)
  reading-request.ts           リクエストボディの検証(2つのAPIルートで共通)
  api-error.ts                 SDKの例外をHTTPステータスと画面メッセージに変換
```

テストは各モジュールに `*.test.ts` を併置しています(`npm test` で65件)。

## 判定ロジック

`noul`タイプ(yes/noの確率を返すプリミティブ)の質問「このカナはこの漢字に対して一般的な読み方か」を
Jevに投げ、返ってくる確率(0〜1)を3段階に分けています(`lib/verify-reading.ts`):

| probability | verdict     | 表示   | 意味                                     |
| ----------- | ----------- | ------ | ---------------------------------------- |
| 0.85 以上   | `plausible` | 一般的 | 辞書的・慣用的に広く使われる読み         |
| 0.3 〜 0.85 | `review`    | 要確認 | 判断が分かれる。人による確認を推奨       |
| 0.3 以下    | `unlikely`  | 非標準 | 典型的でない読み方。誤入力の可能性あり   |

**重要な注意**: これは「読みの一般性・典型度」の推定であり、戸籍上の正誤を保証するものではありません。
日本語の人名には当て字や特殊な読み(いわゆるキラキラネーム等)が実在するため、`unlikely`判定
= 誤りとは限りません。実運用では閾値を実データで検証し、`review`/`unlikely`は人による最終確認に
回すフローを推奨します(このアプリのフッターにもその旨を明記しています)。

## 入力の正規化

ふりがなは**ひらがな・カタカナ・半角カナのいずれでも入力できます**。判定前に
`lib/normalize-reading.ts` でひらがなに正規化してからJevに送るため、表記のゆれが判定結果に
乗りません。`やまだたろう` / `ヤマダタロウ` / `ﾔﾏﾀﾞﾀﾛｳ` はすべて `やまだたろう` として評価されます。

| 入力 | Jevに送る値 |
| ---- | ----------- |
| `ヤマダタロウ` | `やまだたろう` |
| `ﾔﾏﾀﾞﾀﾛｳ`(半角、濁点は1文字に合成) | `やまだたろう` |
| `ヤマダ　タロウ`(全角空白) | `やまだ たろう` |
| `ジョージ` | `じょーじ`(長音符は保持) |

処理は NFKC 正規化 → カタカナからひらがなへのコードポイント変換 → 空白の畳み込みです。
実装上の判断は2点あります。

- **姓名の区切りは消さず半角スペース1つとして残します。** 区切りは「誤りの種別」の
  `区切りずれ` 判定の材料になるためです。
- **漢字側にはNFKCをかけません。** 互換漢字(例: U+FA10 の「塚」)が別のコードポイントに
  書き換わると、氏名として違う字を送ることになるためです。空白を畳むだけにとどめています。

ひらがな・カタカナ以外(ローマ字など)は弾かずそのまま通します。その表記が読みとして妥当かの
判断自体はJevに委ねる方針です。

## 画面構成

`http://localhost:3000/` の1画面で、同じ氏名を Jev の3プリミティブで6観点から同時に評価します。
プリミティブごとに「不確実性の表現力」が違うため、観点に応じて使い分けています。

画面は **1280×720 でスクロールなしに収まる**構成です(実測で確認済み)。

```
┌────────────────────────────────────────────────┐
│ 読み方判定デモ  Jev / TypeSafe System One       │  ダークバー
├──────────────────┬─────────────────────────────┤
│ 1. 氏名とふりがな │ 2. Jev が返した値            │
│   入力 + サンプル │   6観点を1行ずつ              │
│                  │   ラベル / 期待値 /          │
├──────────────────┤   confidence / 確率分布      │
│ 3. コードが決めた │   + model・トークン・往復時間 │
│   しきい値の判定  │                             │
└──────────────────┴─────────────────────────────┘
```

「Jevが返した値」と「こちらのコードが決めたこと」を分けているのが要点です。Jevは値を返すだけで、
`plausible` / `review` / `unlikely` の振り分けはしきい値を持つこちらのコードが決めます。

配色のCSS変数は `app/page.module.css` の `.page` スコープに閉じてあります。

| | 返り値 | `confidence` |
| --- | --- | --- |
| `noul` | 確率1個 (0〜1) | **返らない** |
| `choice` | 選択ラベル + 全ラベルの確率分布 | あり |
| `score` | 確率加重の期待値(小数) + 分布 | あり |

| 観点 | 型 | 内容 |
| ---- | -- | ---- |
| 読みの妥当性 | `noul` | 現行の主判定と同じ命題。`lib/verify-reading.ts` と文言を共有 |
| 読みの一般性 | `score` | 「成立しない」〜「最も自然」の5段階 |
| 読みの成立根拠 | `choice` | 音読み / 訓読み / 名乗り / 当て字 / 不一致 |
| 誤りの種別 | `choice` | 問題なし / 区切りずれ / 濁音の違い / 類似漢字の混同 / 無関係 |
| 創作性 | `score` | 「伝統的」〜「強く創作的」の5段階 |
| 確認の優先度 | `score` | 「確認不要」〜「本人への確認が必須」の5段階 |

要点は2つです。

1. **`noul` には `confidence` がありません。** 確率0.5が「本当に五分五分」なのか「判断材料がない」のか
   区別できません。`score` / `choice` は期待値(または最尤ラベル)と `confidence` が別々に返るため、
   「自信を持って中間」と「そもそも不確か」を切り分けられます。
2. **質問を6問並べてもHTTPの往復は1回だけ**です(サーバー側で並列評価)。画面下部にモデル名・
   所要時間・トークン数・リクエスト数を出しているので、その場で確認できます。

観点が交差するケースがデモの主眼です。例えば「光/らいと」は妥当性が低めに出ますが、誤りの種別は
「問題なし」、成立根拠は「当て字」、創作性は最高段階になります。つまり**誤入力ではなく、非典型だが
正当な読み**です。単一の確率では表せないこの区別を、画面上の読み解きコメントで言語化しています。

### score のラベルについて

モデルに渡すルーブリック(`criteria`)は英文のまま維持し、画面表示用の日本語ラベルを
`lib/analyze-reading.ts` の `SCORE_LABELS_JA` に別途持っています。instructions の言語を変えると
calibration が変わりうるため、表示の都合で本番の文言を書き換えないようにしています。段階数が
ずれていないことはテストで検証しています。バーのラベルにカーソルを載せると、実際にモデルへ
送っている原文が表示されます。

### コスト

6問並べても往復は1回ですが、**instructions と criteria の全文が入力トークンに乗る**ため、入力コストは
問題数にほぼ比例します。実際の消費量は画面下部の `入力トークン` / `出力トークン` で確認できます。
大量データの一括処理では、まず `noul` 1問で振り分け、`review` に落ちたものだけ詳細パネルに回す
2段構成が合理的です。

## ローカル端末での実行手順

必要なもの: **Node.js 20以上**(`@typesafe-ai/sdk`の要件)と、TypeSafeのAPIキー。

### 1. APIキーを取得する

[console.typesafe.ai/keys](https://console.typesafe.ai/keys) にログインしてキーを発行します。

### 2. 依存パッケージをインストールする

```powershell
cd C:\temp\kanji-reading-checker
npm install
```

### 3. APIキーを設定する

`.env.example` を `.env` にコピーし、`TYPESAFE_API_KEY` に発行したキーを貼り付けます。

```powershell
Copy-Item .env.example .env
notepad .env
```

```dotenv
TYPESAFE_API_KEY=<発行したAPIキー>
```

`.env` は `.gitignore` 済みなのでコミットされません。シェルの環境変数として渡しても動作します
(その場合 `.env` の値より優先されます):

```powershell
$env:TYPESAFE_API_KEY = "<発行したAPIキー>"
```

### 4. 開発サーバーを起動する

```powershell
npm run dev
```

`http://localhost:3000` を開き、サンプルを押すか、氏名とふりがなを入力して「判定する」を押します。

### 本番ビルドで確認する場合

```powershell
npm run build
npm start
```

`npm run build` はAPIキーがなくても通ります(クライアントは初回リクエスト時に生成されるため)。

`next dev` と `next build` は同じ `.next` を使うため、両方を行き来すると古い成果物が残ることがあります。
表示がソースと合わないときは `.next` を消してやり直してください。

```powershell
Remove-Item -Recurse -Force .next
```

### うまく動かないとき

| 症状 | 原因と対処 |
| ---- | ---------- |
| 「TypeSafe APIの認証に失敗しました」 | `TYPESAFE_API_KEY` が未設定か無効です。`.env` の値を確認し、設定変更後はサーバーを再起動してください |
| 「リクエストが集中しています」 | レート上限(429)です。SDKが自動でリトライしたうえで失敗しています。しばらく待ってください |
| 「判定中にエラーが発生しました」 | 通信エラー・タイムアウト・TypeSafe側の障害です。サーバー側のコンソールに元の例外が出力されます |
| `EBADENGINE` 警告 | Node.jsが20未満です。`node -v` で確認してください |
| `Hydration failed because the server rendered HTML didn't match the client` | `.next` のビルドキャッシュが古い状態です。ルートやCSSモジュールを差し替えた直後に起きます。devサーバーを止めて `.next` を消してから再起動してください |

調査のためリクエスト/レスポンスの中身を見たい場合は `TYPESAFE_LOG_LEVEL=debug` を設定します。
ただし**氏名がそのままログに出る**ため、一時的な用途に限ってください。

## テスト

```bash
npm test
```

TypeSafe APIは呼びません。クライアントのスタブで判定ロジックと送信内容を、SDK例外のHTTPステータス
変換を、`react-dom/server`でデモ画面のレンダリングを検証します。

実際のJevの応答精度を検証する場合は、正解が分かっているサンプルを多数用意し、確率と実際の正誤を
比較しながら閾値(0.85 / 0.3)を調整してください。UIまで通した動作確認をAPIキーなしで行いたい場合は、
`TYPESAFE_BASE_URL` をローカルのスタブサーバーに向ける方法が使えます(SDKがこの環境変数で
エンドポイントを差し替えられるため)。

## リトライとタイムアウト

SDKが既定で処理します(1回の試行につき10秒でタイムアウト、最大2回リトライ、429/5xx/接続エラーを
指数バックオフで再試行、`Retry-After`を尊重)。挙動を変える場合は`lib/verify-reading.ts`の
`new TypeSafeClient()`に`timeout`・`retry`を渡してください。

## デプロイ

Vercel・Cloud Run・自前のNodeサーバーなど、Next.jsが動く環境ならどこでも構いません
(Vercel AI Gatewayに依存しなくなったため、Vercel固有の設定は不要です)。デプロイ先で
`TYPESAFE_API_KEY` をシークレットとして設定してください。Vercelの場合:

```bash
vercel env add TYPESAFE_API_KEY production
vercel deploy --prod
```

APIキーはサーバー側(APIルート)でのみ使用しており、ブラウザには渡していません。

## 個人情報の取り扱い

氏名は個人情報にあたります。TypeSafeは[ユーザーデータでモデルを学習しないと明言](https://docs.typesafe.ai/legal)
していますが、**Zero Data Retention (ZDR) はエンタープライズ契約での提供**です。以前の
Vercel AI Gateway経由の実装ではリクエスト単位で`zeroDataRetention: true`を指定していましたが、
TypeSafeのAPIを直接呼ぶ構成には同等のリクエストオプションがありません。ZDRが必須の要件なら
`privacy@typesafe.ai` に問い合わせて契約を結んでください。

## 既知の制約・拡張候補

- 大量の氏名データを一括チェックする場合は、まず一般的な読みを形態素解析辞書(例: SudachiPy等)で
  判定し、辞書でカバーできない/競合するケースのみJevに送る2段構成にすると、コストと精度の両方で
  有利です。その一段目には `noul` 1問だけの `/api/verify-reading`(`lib/verify-reading.ts`)が
  使えます。画面からは呼んでいませんが、一括処理用に残しています。
- 6観点は初期案です。閾値と同様、実データで観点とルーブリックを調整してください。
  同一人物判定(名寄せ)のように `state` の形が変わる観点は、別のエンドポイントに分けるのが素直です。
- 確認履歴はありません(1件ずつ判定する構成です)。
- 履歴はブラウザのメモリ内のみで保持しています(リロードで消えます)。永続化が必要な場合はDBの追加を
  検討してください。
- 閾値(0.85 / 0.3)は初期値です。実データで調整してください。
